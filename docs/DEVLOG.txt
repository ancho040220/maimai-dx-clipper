  [프로젝트 개요]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  목적  : YouTube VOD/라이브에서 maimai DX 레이팅 상승 구간을 자동 감지하여
          하이라이트 클립을 추출하고 YouTube에 업로드하는 자동화 도구

  최종 기술 스택
  ├─ YOLO (best_nano.pt)    — 인게임 화면 bbox 감지 및 1000×1000 크롭
  ├─ Tesseract OCR          — 레이팅 숫자 판독
  ├─ PaddleOCR              — 난이도 뱃지 및 달성률 숫자 OCR
  ├─ CLOVA OCR (Naver)      — 일본어 곡명 인식
  ├─ OpenCV                 — 템플릿 매칭 (게임 모드 판별)
  ├─ yt-dlp                 — YouTube 영상 다운로드 / 스트림 URL 추출
  ├─ ffmpeg                 — 클립 커팅 / 라이브 롤링 녹화
  ├─ diving-fish API        — 레벨 상수 DB (24h 캐시)
  ├─ dxrating (gekichumai)  — 곡 목록 DB (7일 캐시, 퍼지 매칭용)
  ├─ PyQt5 QWebEngineView   — GUI 윈도우
  ├─ QWebChannel            — Python ↔ JavaScript 브릿지
  └─ React + Babel (로컬)   — UI 렌더링 (인터넷 불필요)

  [1단계] 초기 스크립트 개발 — scanner.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ■ 프로젝트 시작
    요청 → YouTube 영상에서 "でらっくす RATING" 텍스트 영역을 스캔해
            레이팅 상승 내역을 추출하는 프로그램

  ■ 초기 구현: scanner.py
    - yt-dlp로 영상 다운로드
    - OpenCV로 1fps 프레임 추출
    - 색상 휴리스틱 필터로 레이팅 화면 판별
    - Claude Vision API (Anthropic) 로 숫자 OCR
    - 레이팅 상승 시 타임스탬프 + YouTube 링크 출력

  ■ OCR 엔진 교체: Claude Vision → Gemini API
    이유 → Claude API는 유료, 무료 Gemini로 교체
    - google-generativeai 패키지 사용
    - 분당 15회 한도 대응: API 호출 사이 5초 대기 추가
    - deprecated google.generativeai → google-genai 패키지로 재교체

  ■ 기능 추가
    - --start, --end 옵션으로 분석 구간 지정
    - 영상을 프로젝트 폴더에 고정 저장
    - 레이팅 하락 불가 특성 반영 → 이전값보다 낮으면 OCR 오류로 무시
    - 300점 이상 급등 필터 (오인식 방지)
    - 같은 프레임 3회 다수결 OCR → 이후 3가지 전처리 병렬 다수결로 개선
      (색상 마스킹 / CLAHE+Otsu / 밝기 이진화)

  ■ 영상 스트리밍 분석 시도 → 실패
    목표 → 영상 저장 없이 1fps 이미지만 받아 분석
    결과 → ffmpeg 필요로 구현 복잡, 우선 보류

  ■ OCR 엔진 전면 재검토
    시도 순서: PaddleOCR(Python 3.14 비호환) → EasyOCR(느림) →
              RapidOCR(정확도 낮음) → Tesseract 최종 채택

  ■ 구조 개선: AI 제거 + Tesseract 고정
    - AI 기반 OCR 완전 제거 (API 비용 / 속도 문제)
    - ffmpeg 1fps 스트리밍 분석 방식 도입
    - 분석 완료 후 result_images/ 자동 삭제

  ■ 레이팅 화면 판별 방식 진화
    1차: 색상 기반 (yellow_ratio + brightness)
    2차: 진단 모드로 실제 프레임 분석 → 임계값 실측 확정
         brightness > 150 AND yellow_ratio > 0.08
    3차: 색상/밝기 필터 모두 제거 → 모든 프레임 Tesseract OCR 직접 필터

  ■ UI 개선
    - MIN_GAP 버그 수정 (전환 프레임 타이머 오염 문제)
    - URL 변경 시 자동 재다운로드
    - 실행 시 URL·시작/종료 시간·시작 레이팅 대화형 입력
    - 60초마다 진행 상황 출력
    - 소요 시간 출력

  [2단계] YOLO 기반 구조 고도화 — scanner_parallel.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ■ YOLO 머신러닝 기반 구조 전환
    기존 → 색상/좌표 기반 화면 판별 (해상도마다 다른 좌표 필요)
    변경 → best_nano.pt로 인게임 화면 bbox 감지 → 1000×1000 크롭
    효과 → 어떤 해상도의 방송이든 동일한 고정 좌표로 처리 가능
    OCR 영역 → GAME_ROI = [478, 451, 809, 547] (1000×1000 기준 고정)

  ■ 프로필 시스템 제거
    이유 → YOLO 1000×1000 정규화로 좌표가 항상 동일
    제거 항목: region_config_*.json, region_preview_*.png, --profile 옵션 등

  ■ GPU 가속 설정
    환경 → RTX 5060 + CUDA 13.1 + Python 3.14
    설치 → torch cu128 버전으로 CUDA 연동
    발견 → 병목이 YOLO(5.8ms)가 아닌 Tesseract OCR(99ms)임을 실측 확인
    대응 → 불필요한 OCR 호출 횟수 줄이기 방향으로 설계

  ■ 칼레이도스코프 모드 감지 개발
    목표 → 칼레이도 모드인지 일반 모드인지 자동 판별

    1차 시도: 원형 링 템플릿 매칭 → 이펙트로 인한 오감지 多
    2차 시도: HoughCircles → 오감지 多

    최종 방법: KALEID_FIN_ROI [73, 605, 227, 757] 영역의 어두운 픽셀 비율
               dark_ratio > 0.02 이면 칼레이도
               실측값 → 일반 모드: ≈ 0.000 / 칼레이도: ≥ 0.04

    이펙트 오판 방지 → 레이팅 상승 전후 1초 여러 프레임의 dark_ratio
                        최댓값으로 판별 (단일 프레임 → 다중 프레임 max)

  ■ 게임 시작 화면 역추적 (_lookback) 기능 구현
    목적 → 레이팅 변동 감지 후 해당 플레이의 시작 시점을 역추적

    4가지 게임 모드 템플릿 매칭:
    - 칼레이도 : KALEID_START_ROI  [302, 145, 691, 208] + sample/kaleid_start
    - 일반     : TRACK_ROI         [385, 85, 545, 150]  + sample/normal_start
    - 퍼펙트   : PERFECT_START_ROI [330, 759, 671, 864] + sample/perfect_start
    - 단위인정 : GRADE_START_ROI   [363, 705, 553, 775] + sample/grade_start

  ■ 병렬 처리 (scanner_parallel.py)
    - 영상을 N개 구간으로 분할
    - 각 구간을 별도 프로세스로 동시 처리
    - 구간 결과 병합 후 중복/오인식 필터링

  ■ 기타 안정화
    - URL 유효성 검사 (http로 시작하지 않으면 오류)
    - 시작 레이팅 필수 입력 강제
    - RATING_MIN = 0 으로 수정 (기존 1000)
    - TRACK_TMPL 폴더 경로를 glob 방식으로 읽도록 버그 수정
    - 불필요한 파일/폴더 정리 (test/, region_config 등)

  [3단계] 파이프라인 통합 + GUI 개발
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ■ pipeline.py — 전체 작업 흐름 통합
    VOD 모드 흐름:
      ① analyze_vod_stream()   — 스트리밍 스캔 (레이팅 변동 감지)
      ② process_vod_entries()  — 다운로드 + 역추적 + 클립 커팅 + 업로드

    라이브 모드 흐름 (LiveMonitor 클래스):
      ① ffmpeg 롤링 녹화 (StreamRecorder, 세그먼트 단위)
      ② 실시간 YOLO + OCR 스캔
      ③ 레이팅 변동 감지 → 버퍼 역추적 → 하이라이트 저장

    병렬 다운로드 + 역추적 구조:
      - ThreadPoolExecutor (DL_WORKERS=3) 로 병렬 다운로드
      - 다운로드 완료 즉시 multiprocessing spawn Pool 로 역추적 제출
      - GPU 환경: 역추적 4개 워커 / CPU 환경: cpu_count 워커

  ■ GUI — PyQt5 QWebEngineView + React
    구조:
      main_gui.py       — 진입점
      ui/web_window.py  — QWebEngineView 윈도우, QWebChannel 설정
      ui/bridge.py      — Python ↔ JS IPC 브릿지 (pyqtSignal / pyqtSlot)
      ui/workers.py     — 백그라운드 스레드 (PipelineWorker, CheckWorker)
      ui/web/index.html — HTML 진입점 (React + Babel 로컬 로드)
      ui/web/app.js     — React UI 컴포넌트
      ui/web/tokens.css — 디자인 토큰 (solved.ac 스타일)

    화면 구성:
      - 메인   : URL 입력 · 상태 확인 · 시작 레이팅/시간 · 실시간 로그
      - 스캔 결과: 감지된 레이팅 변동 목록 (타임스탬프 · 레이팅 · 모드)
      - 하이라이트: 생성된 클립 목록 (크기 · 업로드 상태 · 재시도)

  ■ IPC 신호 체계 (stdout → bridge.py 파싱)
    [DETECT]     — 레이팅 변동 감지됨 (스캔 단계)
    [DETECT_UPD] — 역추적 완료 후 play_t + mode 업데이트
    [HL_ADD]     — 하이라이트 클립 생성됨
    [HL_UPD]     — 업로드 상태 변경 (queued / uploading / uploaded / failed)
    [i/n]        — 진행 단계 (진행률 바 업데이트)

  ■ YouTube 업로드 (youtube_uploader.py)
    - Google OAuth2 인증
    - 자동 업로드 토글 (autoUpload 옵션)
    - 업로드 실패 시 highlights/ 폴더 보존 + UI에서 재시도 버튼 제공

  ■ buffers.py — 라이브 모드 버퍼
    CircularFrameBuffer: 최근 N분 프레임 JPEG 압축 메모리 보관 (≈18MB/6분)
    StreamRecorder    : ffmpeg 세그먼트 롤링 녹화 + 오래된 세그먼트 자동 삭제
    세그먼트 시각 계산 → last_mtime 기준으로 역산 (per-file mtime 지터 방지)

  ■ CSS flex gap 호환성 문제 해결
    원인: Qt5 QWebEngine이 사용하는 Chromium 버전이 낮아
          flex container의 gap 속성을 지원하지 않음 (Chrome 84+ 필요)
    증상: gap: 16px 와 gap: 100px 가 시각적으로 동일하게 보임
    해결: tokens.css의 모든 gap 유틸리티 클래스를
          > * + * margin 방식으로 대체

          .mm .row.gap-N > * + * { margin-left: Npx; }
          .mm .col.gap-N > * + * { margin-top: Npx; }

  ■ 블럭 간 여백 통일
    - 메인 화면의 카드 블럭들: marginBottom: 18 적용
      (URL 카드 / 스탯 그리드 / 페이즈 바 / 로그)
    - 사이드바 Logo·Nav 항목: marginBottom: 14

  ■ URL 카드 내부 여백
    - URL 입력창 ↔ VOD 정보 박스: marginTop 4 → 6px
    - URL 입력창 ↔ 오류 박스: marginTop 4 → 6px
    - URL 영역 ↔ 폼 필드 구분선 (hr): margin 4px → 6px

  ■ 스캔 결과 화면 여백
    - 스탯 카드 그리드 ↔ 결과 테이블: marginBottom: 18

  ■ "확인" 버튼 텍스트 방향 수정
    증상: 체크 아이콘과 "확인" 텍스트가 세로로 쌓여 보이는 문제
    원인: 버튼(.btn)이 inline-flex인데 내부 span도 flex로 감싸 충돌

          flexDirection: "row" / flexWrap: "nowrap" / whiteSpace: "nowrap" 지정

    변경 내용:

        - COOKIES_FILE 상수 완전 제거
        - YTDLP_BROWSER = os.environ.get("YTDLP_BROWSER", "firefox") 추가
        - ytdlp_cookie_args() / ytdlp_cookie_opts() 항상 Firefox 반환 (조건 제거)
      README.md
        - "cookies.txt 만드는 법" 섹션 → "YouTube 로그인 설정" (Firefox 안내)로 교체

  ■ maimai DX NET 연동 기능 개발 (core/maimai_net.py)
    목적: 스트리밍 중 플레이한 곡명·달성률·랭크·배지 정보를 자동으로 가져와
          클립 파일명과 YouTube 업로드 제목/설명에 반영.

    MaimaiNetClient 클래스:
      - browser_cookie3로 Firefox 쿠키 직접 읽기 → requests 세션에 적용
      - iPhone User-Agent로 모바일 버전 접근
      - is_authenticated(): /home/ 리다이렉트 여부로 로그인 상태 확인
      - get_play_log(max_entries): /record/playlogDetail/ 스크래핑
        → played_at, title, difficulty, achievement, rank, fc_type, dx_type 반환
      - get_best_records(difficulty): 난이도별 베스트 기록 스크래핑 (B50 추적용)

    이미지 src 파싱 헬퍼 함수:
      - _parse_diff(src)  : 난이도 이미지 URL → BASIC/ADVANCED/EXPERT/MASTER/Re:MASTER
      - _parse_rank(src)  : 랭크 이미지 URL → S/SS/SSS/SSS+ 등
      - _parse_fc(src)    : FC 배지 이미지 URL → FC/FC+/AP/AP+
      - _parse_dx(src)    : DX 배지 이미지 URL → DX/DX+/FDX/FDX+
      - _parse_achievement(text): 달성률 문자열 → float

  ■ HTML 파싱 버그 수정 — played_at = None 문제
    증상: get_play_log() 반환 항목 전체에서 played_at = None.
    원인: 날짜 요소의 실제 클래스가 "sub_title t_c f_r f_11" (다중 클래스)인데
          코드가 "gray f_13", "f_13", "playlog_date" 만 탐색.
    수정: el.find(class_="sub_title") 을 첫 번째 후보로 추가.
          BeautifulSoup의 class_ 파라미터는 다중 클래스 포함 검색이므로 정상 매칭.

  ■ HTML 파싱 버그 수정 — 곡명/달성률/랭크/배지 전부 None
    증상: title, achievement, rank, fc_type, dx_type 모두 None.
    원인: playlog_top_container div는 난이도 이미지와 날짜만 포함.
          곡명·달성률·랭크·배지는 형제 요소(sibling)에 위치.
    수정: _parse_entry() 내에서 scope = el.parent 로 확장해
          형제 요소까지 포함하여 탐색.

  ■ 곡 정보 매칭 기능 (core/pipeline.py)
    match_playlog_to_history():
      - stream_start_utc + 경과 시간 = 결과 UTC 시각 계산
      - maimai DX NET의 played_at (KST) 와 ±90초 허용 오차로 1:1 매칭
      - bisect 이진 탐색으로 O(n log m) 효율 탐색

      - 목표보다 tol_sec(30초) 이상 오버슈트 시 seek_pos를 앞으로 당겨 재시도
      - backoff 공식: seek_pos = max(scan_floor, seek_pos - overshoot × 1.5)
      - stuck 감지: 이전 착지와 같은 위치면 강제 -5분 후퇴
      - 최대 5회 재시도
    연동:
      - _worker(): HTTP URL이면 _seek_verified() 사용, 로컬 파일은 기존 방식 유지
      - actual_start 변수로 실제 착지 위치를 frame_num, seg_duration,
        last_result_time 계산에 반영 (부정확한 progress % 방지)
      - scan_parallel(): worker_args에 scan_floor=start_sec 추가
        (구간 시작 전으로 seek하지 않도록 하한선 보장)

  ■ 버그 수정: 세그먼트 경계 blind spot 수정 (scanner_parallel.py)
    문제: _seek_verified의 허용 오차(tol_sec=30초)로 인해 각 워커가
          세그먼트 시작점에서 최대 30초 뒤에 착지할 수 있음.

          걸리면 감지되지 않음 (Seeking Inaccuracy / Keyframe Gap 문제).
    수정: 첫 번째 워커를 제외한 모든 워커의 시작을 _OVERLAP(30초)만큼 앞당김.
            max(start_sec, start_sec + i * seg_len - _OVERLAP)
          tol_sec 이내 오버슈트가 발생해도 경계 이전 구간을 반드시 커버.
          겹치는 구간의 중복 감지는 merge_and_detect의 1초 dedup으로 처리됨.
    효과:
      수정 전 → 워커 경계마다 최대 30초 blind spot 존재 (결과 누락 가능)
      수정 후 → 경계 blind spot 완전 제거 (오버슈트 최대치와 overlap을 일치)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  · Qt5 QWebEngine의 Chromium은 flex gap을 지원하지 않음.
    → gap 대신 > * + * { margin } 패턴 사용.

  · PyThreadState_SetAsyncExc는 C 확장 내부(OpenCV 루프 등)에서 동작하지 않음.
    → 5초 후 QTimer.singleShot으로 QThread.terminate() fallback 필요.

  · multiprocessing Pool.close()는 현재 작업이 끝날 때까지 기다림.
    → 즉시 중단하려면 terminate() 사용.

  · yt-dlp 다운로드 구간은 --download-sections "*시작-종료" 옵션으로 지정.
    → 소요 시간이 구간 길이에 비례 (300초 타임아웃 설정).

  · 라이브 스트림 재연결 시 반드시 기존 VideoCapture를 release() 후 새로 생성.
    → 그렇지 않으면 핸들 누수 발생.

  · 세그먼트 파일의 st_mtime은 디스크 저장 지연으로 지터가 있음.
    → 마지막 세그먼트 mtime을 기준으로 SEGMENT_SECS 간격 역산이 더 안정적.

  · CLOVA OCR은 프레임 전체(1000×1000)를 JPEG base64로 전송.
    → 곡명 바가 스크롤 중이면 부분 텍스트만 인식되어 퍼지 매칭 신뢰도 하락 가능.
    → 다중 프레임 투표(ratio ≥ 0.25 포함, confidence ≥ 0.35 채택)로 보완.

  · PaddleOCR 3.x는 Python 3.11에서 NotImplementedError 발생.
    → paddleocr==2.9.1 + paddlepaddle==2.6.2 고정.

  · PaddleOCR을 모듈 임포트 시점에 전역 초기화하면 CUDA DLL이 torch보다 먼저 로드됨.
    → 지연 초기화(lazy init) 패턴으로 첫 OCR 호출 시점까지 초기화 지연.

  · scan_parallel()의 세그먼트 경계 blind spot: _seek_verified tol_sec(30초)만큼
    각 워커 시작을 앞당겨 경계에서 결과 누락을 방지.
    겹친 구간의 중복 감지는 merge_and_detect의 1초 dedup으로 처리됨.

  · ETA 계산은 30초 경과, 진행률 5% 이상인 경우에만 활성화.
    YOLO 모델 초기화(≈10초)로 인해 초기 처리량이 낮게 측정되기 때문.

  · timedelta.seconds는 0~86399 범위의 초 컴포넌트만 반환.
    총 경과 초를 원하면 반드시 int(td.total_seconds()) 사용.

  · YouTubeUploader.authenticate()는 공개 메서드; 내부 _authenticate()를 감쌈.
    파이프라인 시작 전 사전 검증 목적으로만 호출할 것.

  · scan_done 시그널과 scan_finished 시그널의 도달 순서:
    scan_done 먼저 → scanStatus = "scan_done" 설정
    scan_finished 수신 → prev === "scan_done" 이면 idle로 전환하지 않음 (race condition 방지)

  [14단계] 결과화면 OCR 고도화 + UI 버그 수정 + 리팩토링
  작성일: 2026-05-06
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ■ 배경
    maimai DX NET 연동이 완성되면서 결과화면(1000×1000)에서 곡명·난이도·달성률을
    직접 추출하는 result_extractor.py의 정확도가 실용 수준에 도달해야 했음.
    기존 Tesseract + EasyOCR 기반은 일본어 곡명, 3D 버블 폰트 달성률, 장식형
    난이도 뱃지 모두에서 인식률이 낮았고, 근본적인 OCR 엔진 교체가 필요했음.


  ■ 난이도 인식 실패 원인 분석
    증상: 氷滅の135小節 (EXPERT), World's end BLACKBOX (EXPERT) 를 MASTER로 오인식.
    원인 1: 난이도 뱃지 탐색 x 범위가 x=10:230으로 고정되어 있었음.
             앨범 아트가 x=0~220을 차지하므로 뱃지가 앨범 아트 영역에 겹쳐
             제대로 된 뱃지를 보지 못함.
    원인 2: 탐색 범위를 넓히면 레이팅 화면 전체가 포함되어 다른 숫자/텍스트가
             난이도로 오매칭됨.
    해결:
      - _find_text_x_start()로 앨범 아트 우측 경계(x_start)를 동적 탐지.
        dark blue 픽셀이 컬럼의 50% 이상인 최초 열을 앨범 아트 끝으로 판단.
      - detect_difficulty()의 x 범위를 (x_start-10) ~ (x_start+500)으로 설정.
      - 앨범 아트 너비가 다른 스킨에서도 뱃지 위치를 정확히 포착.


  ■ 난이도 OCR 엔진 교체: Tesseract → PaddleOCR
    문제: Tesseract는 뱃지의 >> 화살표 장식 문자와 색상 배경 때문에
          "EXPERT"를 "EXPER7", ">>MASTER" 등으로 오독했음.
    시도:
      - Tesseract --psm 7/8/11 + 다양한 전처리(이진화, CLAHE, 마스킹) 시도 → 모두 실패.
      - HSV 색상 분석 fallback으로 뱃지 색상(녹색=EXPERT, 자주=MASTER 등)을 판별하는
        방식도 구현했으나 스킨·조명 차이로 오판이 잦았음.
      - x=10:800 광역 탐색도 시도했으나 사용자가 "너무 넓다"고 판단하여 기각.
    최종: PaddleOCR 2.9.1 도입.
      - PaddleOCR은 자체 텍스트 영역 탐지를 수행하므로 장식 문자 무시.
      - 뱃지 영역(chip) 전달 후 결과를 _DIFF_NAMES와 fuzzy_match(score≥0.5) 비교.
      - HSV 색상 fallback 코드 전부 제거, UNKNOWN 반환으로 단순화.

    설치:
      pip install paddleocr==2.9.1 paddlepaddle==2.6.2
      (PaddleOCR 3.x는 Python 3.11에서 NotImplementedError 발생 → 2.9.1 고정)


  ■ 달성률 OCR 실패 원인 분석 및 해결
    증상: ocr_achievement()가 None을 반환 또는 MY BEST 값(작은 숫자)을 반환.
    원인 1 — 3D 버블 폰트: maimai DX 달성률 숫자는 입체적이고 그라디언트가
             있는 버블 폰트를 사용. Tesseract로 OTSU, adaptive threshold,
             색상 마스킹, flood fill 등 전처리를 모두 시도했으나 "9.6163%"처럼
             첫 자리가 잘리거나 아예 인식 실패.
    원인 2 — 탐색 영역 부정확: 처음 y=300:430으로 설정했다가 "96.6163%" →
             "9.6163%"로 잘리는 현상 확인 → y=260:440으로 확장 후 y=275:415로 조정.
    원인 3 — MY BEST 중복 탐지: 탐색 영역 내에 현재 달성률과 MY BEST 두 숫자가
             동시에 존재. 순서 기반으로 첫 번째 매칭값을 쓰면 MY BEST가 반환됨.
    해결:
      - PaddleOCR로 교체: 스타일드 폰트 인식율 대폭 향상.
      - 탐색 영역 y=275:415, x=40:680 (1000×1000 기준).
      - 매칭된 값들 중 바운딩 박스 높이(max_y - min_y)가 가장 큰 항목 선택.
        이유: 현재 달성률은 화면에 크게 표시되고 MY BEST는 작게 표시되므로
              박스 높이가 큰 쪽이 항상 현재 달성률.
      - spare_digits fallback: 소수점 없이 숫자만 인식된 경우
        (예: "95" + "7179%") 모든 숫자를 이어붙여 마지막 4자리 앞에 소수점 삽입.


  ■ CUDA DLL 충돌 해결 — PaddleOCR 지연 로딩
    증상: PaddleOCR 설치 후 환경 점검의 GPU(CUDA) 항목이 "PyTorch DLL 로드 실패"
          경고로 전환됨.
    원인: result_extractor.py 모듈 임포트 시점에 PaddleOCR()을 전역 초기화하면
          PaddlePaddle CUDA DLL이 먼저 로드됨. 이후 env_check가 torch를 임포트하면
          torch의 CUDA DLL과 버전 충돌 발생.
    해결: 지연 초기화(lazy init) 패턴 적용.
      _paddle_ocr = None

      def _get_paddle_ocr():
          global _paddle_ocr
          if _paddle_ocr is None:
              from paddleocr import PaddleOCR
              _paddle_ocr = PaddleOCR(use_angle_cls=False, lang='en', show_log=False)
          return _paddle_ocr

      모듈 임포트 시점에는 PaddleOCR을 로드하지 않고, 첫 실제 OCR 호출 시에만
      초기화. web_window.py에서 torch를 사전 임포트하므로 항상 torch가 먼저
      CUDA를 선점하여 충돌 해소.


  ■ 곡명 OCR: CLOVA OCR(Naver Cloud) 도입
    배경: 일본어 곡명(한자·히라가나·가타카나 혼합)은 PaddleOCR의 en 모드로 인식
          불가. 일본어 모드(ja)를 시도했으나 라이선스 모델 오류 발생.
          EasyOCR japan 모드는 속도가 느리고 한자 인식률이 낮았음.
    해결: Naver Cloud Platform의 CLOVA OCR Custom API 사용.
      - 1000×1000 프레임 전체를 JPEG base64로 인코딩하여 API에 전송.
      - 템플릿 설정으로 CLOVA가 곡명 위치를 자체 파악, fields의 inferText를 반환.
      - 응답 텍스트를 normalize_ocr()로 정규화(원문자 변환, 노이즈 제거).
      - API 타임아웃 10초, inferResult != "SUCCESS" 또는 네트워크 오류 시 빈 문자열.
      - 결과를 fuzzy_match()로 곡 DB와 비교(ratio ≥ 0.25 → 투표에 포함).

    인증 파일 관리:
      기존: CLOVA_OCR_URL, CLOVA_OCR_SECRET을 settings.py에 하드코딩.
      문제: 인증 키가 소스코드에 노출됨. git 커밋 시 유출 위험.
      해결: config/credentials/clova_ocr.txt 파일로 분리.
        CLOVA_OCR_URL=https://...
        CLOVA_OCR_SECRET=...
      settings.py의 _load_clova_credentials()가 파일을 읽어 상수 초기화.
      파일 없으면 빈 문자열로 처리(기능 비활성화).


  ■ 환경 점검에 CLOVA OCR 항목 추가 (env_check.py)
    기존: ffmpeg · Tesseract · YOLO · YouTube 로그인 · Google 인증 · GPU 6항목.
    추가: CLOVA OCR 항목 (Google 인증 파일 바로 아래 — 업로드와 비슷한 중요도).
    점검 내용:
      1. clova_ocr.txt 파일 존재 여부 — 없으면 error.
      2. URL·Secret 값이 비어있지 않은지 — 없으면 error.
      3. 빈 이미지로 실제 API 호출:
         - 200 또는 400(이미지 인식 불가가 정상): ok.
         - 401: 인증 실패 error.
         - 그 외 상태코드: warning.
         - 네트워크 오류·타임아웃: warning.
    ThreadPoolExecutor max_workers 6 → 7, 타임아웃 15초 적용.


  ■ UI 버그 수정: 업로드 토글 상태 초기화 문제
    증상: 업로드 기능을 끄고 분석을 돌린 후 스캔 결과 화면에서 메인으로 돌아오면

    해결: autoUpload state를 ScreenMain → App 컴포넌트로 끌어올림(state lift up).
      - App에 const [autoUpload, setAutoUpload] = useState(true) 추가.
      - ScreenMain의 로컬 state 제거, props(autoUpload, setAutoUpload)로 수신.
      - 화면 전환과 무관하게 App 레벨에서 상태 영속 유지.


  ■ OCR 디버그 로그 제거 (result_extractor.py)
    제거 항목:
      - "[OCR] 송 바 미검출 → 프레임 스킵" — 매 프레임마다 출력

    이유: OCR 정확도가 실용 수준에 달하여 중간 결과 로그가 불필요.

  ■ 레벨 상수 소스 단일화: chart_db만 사용 (pipeline.py)

  ■ 환경 점검 chart_db 항목 추가 (env_check.py)
    배경: diving-fish API에서 레벨 상수를 가져오는데 캐시가 만료됐거나
          API 연결이 안 되면 영상 제목에 레벨이 표시되지 않음.

      - 캐시 파일(chart_db_cache.json)이 존재하고 mtime이 24시간 이내면 ok.
      - 만료 또는 없음 → ChartDB() 인스턴스 생성으로 실제 API 갱신 시도.
      - 갱신 성공: ok (갱신됨).
      - 갱신 실패 + 만료 캐시 있음: warning (N시간 전 캐시 사용 중).
      - 갱신 실패 + 캐시 없음: error.
    순서: cuda 바로 위(clova_ocr 다음)에 배치.
    max_workers 7 → 8, timeout 15초 적용.

    배경: num_workers=0(자동)일 때 워커 수를 하드코딩(4)으로 고정했음.
          시스템마다 CPU 코어 수·VRAM·가용 RAM이 달라 최적 워커 수가 다름.
    구현: _auto_workers() 함수 신규 추가.

      RAM 기반:
        가용 RAM에서 4GB 여유를 뺀 뒤 워커당 2GB 할당 가정.
        by_ram = max(1, int((avail_gb - 4.0) / 2))

      CUDA 모드:
        by_cpu  = max(1, cores - 1)
        by_vram = max(1, int(vram_gb - 2))       # VRAM에서 2GB 여유
        vram_cap = 4 if vram_gb < 8 else
                   6 if vram_gb < 16 else 8       # VRAM 티어 상한
        result = min(by_cpu, by_ram, by_vram, vram_cap)

      CPU 모드:
        by_cpu  = max(1, cores // 2)
        cpu_cap = 2 if cores < 8 else
                  4 if cores < 16 else 6          # 코어 수 티어 상한
        result = min(by_cpu, by_ram, cpu_cap)

    효과:
      RTX 5060(8GB VRAM), 16코어, 16.5GB 가용 RAM 기준:
        CUDA 모드: vram_cap=6, by_vram=6, by_cpu=15, by_ram=6 → 워커 6개
        CPU 모드:  cpu_cap=6,  by_cpu=8,            by_ram=6 → 워커 6개

  [2026-05-08] 달성률 MY BEST 오인식 버그 수정 (core/result_extractor.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ■ 증상
    maimai DX 결과 화면에서 현재 달성률 대신 MY BEST 값이 기록됨.
    예) 현재 점수 99.9430%, MY BEST 99.7909% → 99.7909%로 저장.

  ■ 원인 분석
    PaddleOCR이 대형 화려한 폰트의 현재 점수를 파편으로 분할 감지:
      '99'    y_center≈25  (크롭 상단 경계에 걸려 미감지)
      '.9430' y_center≈79
      '%'     y_center≈92
    반면 MY BEST "99.7909%"는 소형 폰트라 완전하게 인식 (y_center≈9.5).
    candidates에 MY BEST만 들어가고 현재 점수 파편은 재조합에 실패.

    재조합 실패의 직접 원인:
    1. 크롭 시작점(y=275)이 대형 "99" 상단과 겹쳐 PaddleOCR이 "99"를 아예 미감지.
    2. 하단 파편 필터 기준(y_center >= 30)이 y_center≈25인 "99"를 잘못 배제.
    3. MY BEST 판별 기준이 y_center 고정값이라 크롭 크기 변화에 취약.

  ■ 수정 내용

  ■ 프레임 추출 방식 교체: cap.read() + sleep → FFmpeg rawvideo 파이프
    기존: cv2.VideoCapture로 스트림 URL 열고 cap.read() 후 1초 sleep 반복.
    문제: OpenCV 내부 버퍼링으로 실제 수신 시각과 read() 시각이 불일치.
          sleep(1)이 정확한 1fps를 보장하지 않아 레이팅 감지 타이밍이 부정확.
    수정: FFmpeg를 `-vf fps=1 -f rawvideo -pix_fmt bgr24 pipe:1`로 실행,
          stdout에서 프레임 크기 단위로 블로킹 read → PTS 기반 정확한 1fps 보장.
          스트림 끊김 시 short read 감지 후 재연결 (최대 15회).

  ■ ffprobe 해상도 사전 조회 추가 (_get_stream_resolution)
    FFmpeg 파이프는 frame_size = width × height × 3을 알아야 정확히 read 가능.
    ffprobe로 스트림 해상도를 사전 조회, 실패 시 1920×1080 폴백.

  ■ CUDA 하드웨어 가속 적용
    torch.cuda.is_available() 시 FFmpeg에 `-hwaccel cuda` 추가.
    디코딩 부하를 GPU로 오프로드해 CPU 점유율 감소.

  ■ 스레드 YOLO 경합 문제 확인
    _on_rating_change 스레드들이 self.yolo를 공유 → GPU 동시 접근 경합.
    (Phase 1/2 재설계 시 구조 변경으로 자연스럽게 해소됨)

                           _monitor_loop() rawvideo 파이프 방식으로 전면 교체

      리팩토링 중 _worker()의 재연결 블록을 _open_and_seek() 호출로 교체하면서

    수정:
      line[9:] → line[10:]
    파일: ui/bridge.py (_on_log)

    수정:
      파일별 try: f.unlink() / except OSError: pass 추가
    파일: ui/web_window.py (launch_gui 파일 삭제 블록)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ■ 증상
    라이브 모드에서 OCR 인식 실패 시 저장된 결과 화면 이미지가
    결과 화면이 아닌 게임플레이 화면으로 잘못 추출됨.

  ■ 원인
    기존 구현은 세그먼트 파일에서 result_ts_wall 근처 구간을 잘라 OCR 프레임을
    추출했는데, 두 ffmpeg 프로세스(1fps 파이프, StreamRecorder)가 같은 URL에
    독립적으로 연결되어 버퍼링 지연이 서로 달랐다.
    세그먼트 파일의 mtime 기준 시각과 1fps 파이프의 result_ts_wall(time.time()) 간
    timing drift가 발생해 전혀 다른 구간의 프레임이 추출됨.

  ■ 수정
    CircularFrameBuffer.get_frame_near(result_ts_wall)를 직접 호출하여 프레임 추출.
    1fps 파이프가 result_ts_wall 시점에 감지한 프레임을 그대로 버퍼에서 읽으므로
    timing drift 없음.
    _extract_ocr_frame_from_segments() 메서드 및 관련 import 삭제.

  ■ 변경 파일
    core/live_monitor.py — _on_rating_change() OCR 프레임 추출 로직 교체
                           _extract_ocr_frame_from_segments() 삭제

  ■ 문제
    cut_highlight(play_wall, result_ts_wall, ...) 에서 두 인자가 서로 다른
    좌표계를 사용하고 있었다.
      play_wall      — 세그먼트 mtime 기반 역산 → 세그먼트 내부 시각
      result_ts_wall — time.time() (1fps 파이프 벽시계) → 별개 기준
    두 ffmpeg 프로세스 간 버퍼링 차이로 drift가 발생하며,
    HIGHLIGHT_POST=10s로 이 오차를 보정하고 있었음.

  ■ 수정
    result_ts_wall 대신 세그먼트 좌표계 안에서 result 시각을 계산:
      result_wall_for_clip = play_wall + (result_stream_sec - play_stream_sec)
    play_wall이 세그먼트 기준 정확한 시작점이고,
    (result_stream_sec - play_stream_sec)은 1fps 파이프 내부의 상대값이라
    절대 drift가 상쇄된다.
    HIGHLIGHT_POST는 이제 drift 보정이 아닌 순수 여유 패딩으로만 동작.

                           result_wall_for_clip 계산 추가, result_ts_wall 교체
